# po-workbench 新手入口

本项目的使用者可能不熟悉 AI 助手，不知道能做什么。本技能的作用是：在该出现的时候给出三个明确的入口，点了就直接干活，不用用户自己想怎么问。

## 一、什么时候弹选项

满足以下任一条件时，调用一次快捷选项工具：

1. 会话第一轮，用户只打招呼或信息量极少（"你好""在吗""你是谁""你能干啥"）。
2. 用户明确表示不知道做什么 / 不知道怎么用（"我该干啥""能做什么""怎么用"）。
3. 一个任务刚交付完成，用户没有给出下一步。

**不要弹的情况**：任务正在执行中；用户已经明确提出了需求；同一组选项刚从上一轮弹出且用户还没给出新方向。任务中间不要打断节奏。

调用方式：先用 `tool_search` 查 `interaction.suggest` 拿到参数，然后**先输出完整回答正文，最后再调用该工具**。参数里给三条文本，每条不得超过 30 字（工具硬限制），不带序号，也不要写"选项一"这类标签。固定用这三条：

- `启动项目：启动 po-workbench 并在浏览器打开`
- `项目介绍：讲讲 po-workbench 是做什么的`
- `项目开发：给 po-workbench 加功能或修 bug`

不要自行改文案、不要增减条数。用户点任意一条后，那条文本会作为新的用户消息发过来，按下面三段路由执行。

## 二、路由识别

收到用户消息后，判断它属于哪一类（用户可能说"1""启动""帮我跑起来""介绍下""改个东西"，按语义判断，不要只看字面）：

- 启动 / 跑起来 / 打开 / 运行 → 走「三、启动项目」
- 介绍 / 是什么 / 做什么 / 了解一下 → 走「四、项目介绍」
- 开发 / 加功能 / 修 bug / 改需求 / 优化 → 走「五、项目开发」
- 都不像，是自由提问 → 正常对话回答，不要强行把话题拉回选项

## 三、启动项目

1. **确定仓库根目录**：优先看当前工作目录的 `package.json` 里 `name` 是否为 `po-workbench`，是就直接用；不是就解析本技能目录的真实路径（本技能通常是以软链接形式安装的），仓库根 = 真实路径的上两级：

```bash
python3 -c "import os,sys;print(os.path.realpath(sys.argv[1]))" "<本SKILL.md所在目录>"
```

2. **检查 Node 版本**：需要 `^20.19.0 || >=22.12.0`。版本不符时先执行 `nvm use 22`（有 `.nvmrc`），仍不符就如实说明并停下。
3. **检查依赖**：`node_modules` 不存在时执行 `npm install`。
4. **启动**：在仓库根执行 `npm run dev`，放到后台运行（不阻塞），等日志里出现 `Local:` 或端口号再继续。若 5173 已被占用，读取日志里的实际端口（Vite 会自动往上找空闲端口），或加 `--port 5174`。
5. **打开页面**：默认在**豆包自己的浏览器面板**里打开，不要用系统默认浏览器。做法：先 `tool_search` 查 `sidebar_create_tab`，再以 `target = {"type": "browser", "url": "http://localhost:<实际端口>"}`、`activate = true` 新建浏览器标签页。只有在 `sidebar_create_tab` 不可用时，才退回系统默认浏览器（macOS 用 `open <url>`），并在汇报里说明退回了。
6. **汇报**：说明已在右侧工作区打开、给出实际地址、当前状态（后台运行中）、怎么停止（`Ctrl+C` 或告诉我停）。另外提一句可以继续点「项目介绍」或「项目开发」。

失败处理：把报错原文贴出来，指出可能原因（Node 版本、依赖未装、端口占用），不要瞎猜、不要假装已经打开。启动成功后不要 kill 进程。

## 四、项目介绍

读取仓库内 `skills/po-workbench-entry/project-intro.md`，用**大白话**讲，控制在 5～8 句，覆盖：这是什么、现在能干什么、还没做什么、想改东西怎么开口。不要堆技术栈清单，不要贴目录树。用户追问细节时再去看代码或 README。

## 五、项目开发

1. 先问一句：是"加功能"还是"修 bug"（用自然语言问，不要用选项工具）。
2. 定位代码：按需求找 `src/pages`、`src/layouts`、`src/components` 下对应文件，同时看一眼 `README.md` 里的开发约定（中文注释、接口异常处理、`@/` 别名、改代码同步改测试）。
3. 给方案：说清要改哪些文件、影响范围、有没有兼容风险，**等用户确认后再动手改**。
4. 改完自检：`npm run typecheck`；涉及逻辑时 `npm test`。
5. 汇报改了什么、怎么验证（页面上点哪里能看到效果）。

## 六、规则

- 三项文案固定，不临时改写；不在任务中途插播选项。
- 用户点了选项就直接执行，不再反问"你确定要启动吗"。
- 用户自由提问时正常回答，选项只在上述时机出现。
- 对不熟悉技术的使用者，少用术语，先说清楚"这件事现在变成什么样了"。
- 启动、运行这类本机动作，失败必须如实报告，不粉饰。
