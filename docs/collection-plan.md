# 邮政企业采购订单采集方案（探测版）

> 记录时间：2026-11-18
> 目标系统：ECShop/ECSCP 后台 `mobile/backend/order.php`
> 当前阶段：只读探测完成，等待确认全量通道与详情补全策略

## 1. 探测结论

### 1.1 列表接口

- 地址：`POST order.php?is_ajax=1`
- 请求体：`application/x-www-form-urlencoded`
- 响应：JSON 信封 `{ error, message, content }`，`content` 是 HTML 表格，不是订单 JSON 数组。
- 分页：只有 `page` 有效；服务端固定 10 单/页；`start`、`page_size`、`record_count` 基本无效。
- 全量规模：约 497,880 单，全量列表需要约 49,788 次请求。

### 1.2 详情接口

- 地址：`GET order.php?act=info&order_id=...`
- 返回 HTML；加 `is_ajax=1` 仍是同样的 HTML，没有 JSON 变体。
- 包含审核人链、操作日志、收货人联系方式等列表没有的字段。

### 1.3 登录态

- 未登录 GET 列表页：`302 Location: privilege.php?act=login`
- 未登录 POST 查询接口：HTTP 200 + `{"error":1,"message":"对不起,您没有执行此项操作的权限!","content":""}`
- 可用于「检测登录态」：先 GET 列表页看是否 302，再 POST 一次 `page=1` 查询看 `error` 是否为 0。

### 1.4 官方导出（重要发现）

列表页存在三个导出入口：

| 入口 | 接口 | 说明 |
| --- | --- | --- |
| 导出订单 | `export_order_list.php` | 列表级导出 |
| 导出完整订单 | `export_order_pro.php` | 完整订单导出，异步任务 |
| 按月打包导出 | `export_order_month.php` | 按自然月生成 `2026-01.xls` 并打 zip，代码注释注明仅超级管理员 |

导出任务列表：`export_task.php?act=list`；下载：`export_task.php?act=download&id=...`

已下载现有任务 5566（未创建新任务）：

## 3. 采集策略

### 3.1 全量历史

首选官方按月打包导出：

1. 从 2019-10 到当前月，按月提交导出任务。
2. 轮询 `export_task.php?act=list`，完成后下载 zip。
3. 解压得到每月 `.xls`（HTML 表格），用 cheerio 解析。
4. 解析后写 SQLite；临时文件解析完即删，不保存原始 HTML。

收益：35 列、全量商品行、完整手机号、税务字段；避免 49,788 次列表请求和约 49.7 万次详情请求。

风险：按月导出仅超级管理员可用；任务生成耗时未知；需先做单月测试。

兜底：`export_order_pro.php` 按时间段导出；再兜底才是列表 + 详情抓取。

### 3.2 增量更新

用户点击「增量更新」触发，不做定时任务：

1. 默认取最近 7 天（带重叠，防止漏单/补录单），可选日期范围。
2. 调列表接口按时间过滤，取新增订单号。
3. 对新订单抓详情，补审核人/日志等字段。
4. 事务 upsert 到 SQLite。
5. 财务/税务字段可等月末官方导出再对账补齐。

### 3.3 详情补全

详情独有字段采用按需补全：

- 打开订单详情时，若尚未补全则实时抓一次并落库。
- 或对选定时间段执行「批量补全详情」。
- 不建议对 49.7 万单全量预抓：按 2 请求/秒约 69 小时，按 0.5 请求/秒约 276 小时，且对目标系统压力大。

## 4. 技术架构

- 前端：React 19 + antd 6.7.1 + Vite + React Router。
- 本地服务：Node 22（要求 20.19+/22.12+），只监听本机，前端通过本地 token 调用。
- 数据库：SQLite + better-sqlite3（Mac/Windows 均有预编译包）。
- HTTP：undici/fetch + tough-cookie 管理 Cookie Jar。
- HTML 解析：cheerio。
- 压缩包：adm-zip。
- 并发：p-limit，默认低并发，失败指数退避。
- 存储：只存结构化字段和解析后的行 JSON；不存原始 HTML、不存导出原始文件。
- Cookie：AES-256-GCM 加密存本地；前端不回显、不写日志。
- CSRF：每次从列表页动态解析，不持久化。

## 5. 登录态检测

工作台提供「检测登录态」按钮：

1. GET 列表页，禁止自动跟随跳转；若 302 到 `privilege.php?act=login` 则失效。
2. POST 一次 `order.php?is_ajax=1` 查询 `page=1`，若 `error !== 0` 则失效。
3. 同时解析三个 CSRF token，供后续导出/查询使用。

Cookie 更新流程：粘贴新 Cookie → 先检测 → 通过后加密保存；失败则提示重新获取。
