# 邮政企业采购订单采集方案

> 记录时间：2026-11-18
> 目标系统：ECShop/ECSCP 后台 `mobile/backend/order.php`
> 当前阶段：已放弃官方导出通道，保留「列表全量扫描 + 详情全量补全 + 打印预览补全 + 手动增量」

## 1. 探测结论

### 1.1 列表接口

- 地址：`POST order.php?is_ajax=1`
- 请求体：`application/x-www-form-urlencoded`
- 响应：JSON 信封 `{ error, message, content }`，`content` 是 HTML 表格，不是订单 JSON 数组。
- 分页：只有 `page` 有效；服务端固定 10 单/页；`start`、`page_size`、`record_count` 基本无效。
- 全量规模：约 497,880 单，全量列表需要约 49,788 次请求。
- 分页方向稳定（ASC），可以按页游标断点续跑。

### 1.2 详情接口

- 地址：`GET order.php?act=info&order_id=...`
- 只接受内部数字 `order_id`，不接受主订单编号。
- 返回 HTML；加 `is_ajax=1` 仍是同样的 HTML，没有 JSON 变体。
- 包含审核人链、操作日志、收货人联系方式等列表没有的字段。
- 内部 `order_id` 只能从列表接口获取，所以详情补全必须先跑完列表扫描。

### 1.3 登录态

- 未登录 GET 列表页：`302 Location: privilege.php?act=login`
- 未登录 POST 查询接口：HTTP 200 + `{"error":1,"message":"对不起,您没有执行此项操作的权限!","content":""}`
- 检测方式：先 GET 列表页看是否 302，再 POST 一次 `page=1` 查询看 `error` 是否为 0。

### 1.4 打印预览接口

- 地址：`POST order.php?act=operate`
- 请求体：`checkboxes=<主订单号>`（可重复）、`printing=打印订单`、`batch=1`、`order_id=<主订单号逗号列表>`
- 响应：HTML 片段，整批订单放在同一个 `div#printall` 中，每个订单以 `<h3>订单信息</h3>` 开头，
  后接若干字段 `<div>`、商品 `<table>` 与 `<div>合计</div>`；订单之间没有独立外层容器。
- 单批实测 20 单可全部返回（22 个订单块），没有导出通道那种 50 单/75 行的静默截断。
- 独有字段：完整手机号、下单人姓名、下单人联系方式、完整收货地址、商品含税单价、商品含税小计。
- 只读验证：仅对单个订单 `2019101834008`（内部 `order_id=219`）请求打印，打印前后详情页
  完整 HTML（含操作日志）的 SHA-256 完全一致。该端点名义上是 `act=operate` 批量操作入口，
  客户端只发送 `printing=打印订单`，绝不发送 cancel/remove/confirm 等操作字段。

## 2. 官方导出通道（已废弃）

### 2.1 曾经评估的三个入口

| 入口 | 接口 | 说明 |
| --- | --- | --- |
| 导出订单 | `export_order_list.php` | 列表级导出 |
| 导出完整订单 | `export_order_pro.php` | 完整订单导出，异步任务 |
| 按月打包导出 | `export_order_month.php` | 按自然月生成 `2026-01.xls` 并打 zip，代码注释注明仅超级管理员 |

导出任务列表：`export_task.php?act=list`；下载：`export_task.php?act=download&id=...`

导出文件实际是 UTF-8 HTML 表格伪装成 `.xls`，共 35 列，含完整手机号（列表/详情页为掩码），
以及税额、对帐/开票/收款状态、上级单位、EA 串等导出独有字段。

### 2.2 截断实测结论（放弃导出的直接原因）

2026-11-18 对导出通道做了多轮只读验证，结论是**服务端对每个导出任务有硬上限**：

| 测试方式 | 请求规模 | 实际返回 |
| --- | --- | --- |
| 按月导出 2023-06 | 整月 | 仅 61 行商品明细 / 19 个主订单，文件约 67.89 KB |
| `order_sns` 批量导出 | 40 个主订单 | 33 个主订单 / 71 行商品 |
| `order_sns` 批量导出 | 120 个主订单 | 50 个主订单 / 约 75~80 行 |
| `order_sns` 批量导出 | 40 个多件订单 | 21 个主订单 / 73 行商品 |

- 每个任务最多约 **50 个主订单 / 75~80 个商品行**，超出部分被静默丢弃。
- 任务仍显示「已完成 100%」，不会报错，也没有任何截断提示。
- 文件大小在约 67.89 KB 时截断，疑似服务端缓冲区上限。
- 按月导出、`order_sns` 批量导出、列表导出均受同样限制，换参数无法绕过。

要覆盖约 49.7 万单，按 50 单/任务需要近 1 万个导出任务，且无法确认目标系统允许如此高密度的
任务创建；该通道不可用于全量采集。

### 2.3 产品决定

- 彻底移除按月导出/批量导出功能，不再创建任何导出任务。
- 不再读取或保留导出文件；已产生的导出任务记录与导出游标已从本地库清理。
- 历史导出数据中仅保留与列表数据重合的订单：删除仅来源于导出的 1275 单及其商品行，
  保留列表扫描到的 300 单（其中 52 单保留早期的完整手机号等导出字段）。
- 额外字段策略：完整手机号、下单人姓名/联系方式、完整地址与商品含税价改由打印预览通道采集；
  税额、对帐/开票/收款、上级单位、EA 串、商品分类仍无法采集，只存在于早期历史数据。

### 3.5 字段合集结论

- 列表独有：订单备注、商城价、商品件数、物流/单号、订单级审核状态、内部订单 ID。
- 打印预览独有：完整手机号、下单人姓名/联系方式、完整收货地址、商品含税单价/小计。
- 详情独有：购货人、付款/审核/送货时间、收货人邮箱/电话/邮编/单位、品牌、多人审核链、操作日志、合计金额。
- 当前策略：三个通道取并集；同一字段以最新采集到的非空值为准。
  手机号打码值不会覆盖打印预览或历史导出留下的完整值。
- 仍无法采集：税额、不含税单价/金额、增值税率、对帐/开票/收款、上级单位、EA 串、商品分类。

## 4. 采集策略

### 4.1 全量历史

1. **列表全量扫描**：按页游标从头扫到尾，写入订单主信息、商品行、内部订单 ID。
   约 49,788 次请求，固定 10 单/页，可暂停续跑。
2. **详情全量补全**：对缺少详情的订单逐单请求详情，补审核人链、操作日志等字段。
   默认 2 并发、350ms 间隔，约 49.7 万单，预计 69 小时左右，可随时暂停续跑。
   没有内部订单 ID 的订单会被跳过，并在前置检查中提示先跑列表扫描。
3. **打印预览补全**：按主订单编号批量请求打印预览，默认 20 单/批、350ms 间隔，
   补完整手机号、下单人姓名/联系方式、完整收货地址与商品含税价。
   约 2,490 次请求，可暂停续跑；如果某批订单未返回数据，任务会停止并提示稍后重试。

### 4.2 增量更新

用户点击「增量更新」触发，不做定时任务：

1. 默认取最近 7 天（带重叠，防止漏单/补录单），可选日期范围。
2. 调列表接口按时间过滤，取新增订单号。
3. 对新订单抓详情，补审核人/日志等字段；可选是否同时刷新已有订单详情。
4. 事务 upsert 到 SQLite。

### 4.3 合并规则

- 以 `order_sn` 为主键 upsert 订单，`COALESCE` 合并不同通道的字段。
- 商品行按 `itemKey` / 子订单号 / 供应商订单号 / 货号 / 商品名 + 数量对齐。
- 手机号：完整值优先，列表/详情返回的掩码值不覆盖打印预览或历史导出留下的完整值。
- 所有写入使用事务，避免并发任务产生半成品数据。

## 5. 技术架构

- 前端：React 19 + antd 6.7.1 + Vite + React Router。
- 本地服务：Node 22（要求 20.19+/22.12+），只监听 127.0.0.1；前端通过 /api 同源访问。
- 数据库：SQLite + better-sqlite3（Mac/Windows 均有预编译包）。
- HTTP：Node 22 内置 fetch + 自实现 Cookie Jar（支持 Set-Cookie 更新与手动重定向判断）。
- HTML 解析：cheerio。
- 并发：p-limit，默认低并发，失败指数退避。
- 存储：只存结构化字段和解析后的行 JSON；不存原始 HTML。
- Cookie：AES-256-GCM 加密存本地；前端不回显、不写日志。

## 6. 登录态检测

工作台提供「检测登录态」按钮：

1. GET 列表页，禁止自动跟随跳转；若 302 到 `privilege.php?act=login` 则失效。
2. POST 一次 `order.php?is_ajax=1` 查询 `page=1`，若 `error !== 0` 则失效。

Cookie 更新流程：粘贴新 Cookie → 先检测 → 通过后加密保存；失败则提示重新获取。
